# Headless probe for starflight-unity-port

A headless compile check and a play-mode probe for this project. They run Unity in batch mode against the project in the current directory, which can be the main checkout or any git worktree. Each worktree needs its own `Library/`, so the first run in a new one imports everything and takes about four minutes; later runs take 10 to 60 seconds. A GUI Editor that has a different checkout open is not disturbed, but Unity refuses to open a project that another Editor already has open.

Nothing in this folder is part of the game. It sits outside `Assets/`, so Unity neither compiles nor imports it. `probe.ps1` copies `ClaudeProbe.cs` into `Assets/` for one run and deletes it again, and `.gitignore` keeps that copy from ever being committed.

Both scripts start Unity with `--burst-disable-compilation`. With Burst on, every run has Burst load an unsigned DLL it compiled into `Library/BurstCache/JIT/`, and on a computer where Smart App Control enforces its policy Windows blocks that DLL (Code Integrity event 3033, `error code 4551` in the Unity log) and shows a notice that is easily taken for the game being blocked. Burst only speeds up the experimental `TerrainJob` (used by `Test.unity`, not a build scene), so a scenario runs the same without it. The argument is used rather than the environment variable `UNITY_BURST_DISABLE_COMPILATION` because the variable also reaches the script compiler and switches off Burst's IL post-processing there, and the next Editor that runs the project with Burst on then recompiles every script assembly from scratch. Start any other headless Unity on this project with the argument too.

## Requirements

- Windows with PowerShell 7.
- The Unity version named in `ProjectSettings/ProjectVersion.txt`, installed by Unity Hub in its default place (`C:\Program Files\Unity\Hub\Editor\<version>`).
- Python 3 for the two helper scripts.
- Logs go to `%TEMP%\starflight-probe`.

Run everything from the project root.

## Compile check

```powershell
& "DevTools\HeadlessProbe\compile-check.ps1" -Name some-label
```

Prints Unity's exit code, any `error CS`, the `Tundra build` line, the package count, warnings from project code and `git status`. Exit code 0 plus `Tundra build success` means it compiles.

## Play mode probe

```powershell
& "DevTools\HeadlessProbe\probe.ps1" -Scenario h6
```

Copies `ClaudeProbe.cs` into `Assets/`, launches Unity with `-executeMethod ClaudeProbe.Run -probeScenario <name>`, prints the lines the probe logged (`[ClaudeProbe] ...`), then deletes the probe and its `.meta` again. A run takes 20 to 30 seconds. The copy in `Assets/` is ignored by git.

Unity is stopped if it has not come back after 420 seconds. `-TimeoutSeconds 100` shortens that, for a scenario that is expected to hang on the old code: a hang on the main thread also stops the probe's own 120 second watchdog.

`-Graphics` runs Unity without `-nographics`, so it has a graphics device (it still opens no window). A scenario can then render the game's camera into PNG files: `explosionpictures` writes its pictures to `Logs/explosion-pictures/`, `hitpictures` to `Logs/hit-pictures/`, `weaponpictures` to `Logs/weapon-pictures/` `transporterpictures` to `Logs/transporter-pictures/`, `debrispictures` to `Logs/debris-pictures/`, `atmospherepictures` to `Logs/atmosphere-pictures/` `starfieldpictures` to `Logs/starfield-pictures/` `skyboxpictures` to `Logs/skybox-pictures/` and `shippictures` to `Logs/ship-pictures/` (or the folder given with `-probePictures`). `screenpictures` and `starport-screenpictures` render the whole screen as the player sees it (every camera in its order of depth: the views, the console and its displays, the panels) into `Logs/screen-pictures/spaceflight/` and `Logs/screen-pictures/starport/`, and `surfacepictures` and `bridgepictures` the landed ship and the terrain vehicle's screens and the flight scene's docking bay and launch into `Logs/screen-pictures/surface/` and `Logs/screen-pictures/bridge/`, `flightpictures` the flight screens those do not reach (Science's and Navigation's menus, the save panel, combat, the starmap, Log Planet, the descent and the Black Egg's countdown) into `Logs/screen-pictures/flight/` and `intropictures` the pages of the Intro into `Logs/screen-pictures/intro/`, for comparing the port's screens with the original's in `Research/Screenshots/`. The probe cannot judge how a picture looks; a person has to.

What the probe does:

- Opens `Spaceflight.unity` (or `Starport.unity` for scenarios whose name starts with `starport`) and enters play mode.
- **Never touches the real saves.** Between `DataController.Awake` and `Start` it replaces the private `_saveSystem` with an in-memory one, and it refuses to continue unless `DataController` asked that one about every slot. All five slots are therefore new games.
- Puts the player in hyperspace, from where the game drops into the Arth star system by itself. `EnsureCrew()` fills every crew role, as a launched ship always has.
- Waits until the planets of that star system have been generated before it starts the scenario. The game is paused while they are being generated, so a scenario that started earlier would lose about two seconds of every real-time wait.
- Counts exceptions (with their first stack frame), and un-pauses the Editor every tick, because the console's Error Pause preference pauses play mode on the first logged error even in batch mode.

### The playthrough

`playthrough-1` to `playthrough-21` play the game from a new game to the win and Interstel's bonus, each stage from the save the one before left (in `$env:TEMP\starflight-probe\playthrough`), through the real console buttons, with real flight and real driving: the Starport (crew, training, ship configuration, the bank), Arth's system and planet 94 (sensors, analysis, landing, mining, back to the ship), selling the minerals, Sphexi (the Crystal Orb's and the Black Egg's ruins), the Crystal Cone, the Crystal Planet (the Orb against its field, the nexus, the egg armed, the explosion and the bonus) and the way home to the Starport. Run them in order with `& "DevTools\HeadlessProbe\run-playthrough.ps1"` (about 25 minutes; `-From n` goes on from the save of stage n - 1). They are not in `run-all-scenarios.ps1`, since each needs the save of the stage before. Where the game has a bug that would stop it, a stage logs `GAME BUG`, works round it so the later stages still run, and fails a check that names it.

### Before and after

A check that cannot fail proves nothing, so run the scenario on the old code as well:

1. Commit the fix (or copy the fixed files aside).
2. Put the old version of the changed files back, for example `git show origin/master:<path> | Set-Content <path> -Encoding utf8NoBOM`.
3. Run the scenario. It should show the bug.
4. Restore the fixed files and run it again.

Use reflection in the probe for anything that only exists on one side, so the same probe compiles against both.

A change in behaviour gets its scenario in the same pull request. Two open pull requests that both add a scenario touch the same two places in `ClaudeProbe.cs` (the scenario switch and the end of the scenario list), so the second one to merge has to rebase.

### Adding a scenario

Add a `case "<name>":` in `Start()` and an `IEnumerator Scenario...()` method. `python add_scenario.py ClaudeProbe.cs <name> <MethodName> <snippet file>` does both: write the method (and any helpers) to a snippet file first.

Helpers already there: `EnterEncounter`, `LeaveEncounter`, `Kill` (through `CombatController.ApplyDamageToAlien`), `Hit` / `HitsToKill`, `FindEncounter( location, minShips, atOnce, skip, race )`, `ForceVessel`, `FirstLivingAlien`, `BringAliensClose`, `DamageTaken`, `FireRepeatedly`, `Stance`, `Endurium`, `Stored` / `Describe` (the in-memory save slots), `WaitForScene`, `AddPerson`, `EnterOrbit( planetId )`, `WaitForLocation`, `PressButton( buttonSet, index )` (through the button controller), `TerrainVehicleCargo`, `BesideTheVehicle` (where to put a deposit for the Cargo button), `SetInput` / `ConsoleFrameWith` (one frame of the button controller with a stick direction or the fire button held), `Console`, `Dump`, `GetField` / `SetField` / `Call` (reflection, including private members), `FindPanel<T>`, `OpenPanel` / `ClosePanel`, `Check`, `MessagesText`, `MessageList`, `Frames`. End with `Finish( "scenario=... key=value ...", 0 )`. Wrap game calls that may throw in `try`/`catch`, since an exception inside the coroutine stops the scenario and it then ends in `RESULT timeout`.

Pitfalls:

- **Write scenario snippets to a file with an editor, not through a shell heredoc.** An apostrophe in a comment breaks the heredoc, and `'\n'` in C# comes out as a real line break after a round trip through a Python string.
- **The message box text is redrawn in `LateUpdate`.** `MessagesText()` right after a button press shows the old text. Use `MessageList()` (the list in the player data) or wait a few frames.
- **Alien ship types are random.** Call `ForceVessel( encounterId, vesselId )` before entering when the test needs armed ships (a transport has no weapons). The vessels of one race differ in more than weapons (the Elowan warship has a move delay of 2700, the transport and the scout 2200), so a check that does not force the vessel takes what it expects from the vessel of the ship it watched.
- **Real-time checks need tolerance.** Unity caps `Time.deltaTime` on slow frames, and the game is paused whenever a star system is generating its planets (a scenario that changes star system has to wait for `m_starSystem.GeneratingPlanets()` to be false itself). For exact numbers call the update method directly with a time step, or add up `Time.deltaTime` in the coroutine after each `yield return null` and divide by that: the coroutine runs after the `Update` of the same frame, so the sum is the game time the movement it measures took.
- **What moves with the game time moves by a different amount in every run.** A shape measured a frame after it was made has had that frame's update (a wreck's `DebrisTumble`), and an animated model is never the same shape twice (the Mysterion's orbs): measure in the same frame, or measure the template at rest. To see whether a check depends on frame time, set `Time.captureDeltaTime = Time.maximumDeltaTime` around it for one run: every frame then takes a third of a second.
- **An alien line is not said as the game data has it.** `Encounter.AddComm` fills in the player's ship (`&`), the player's captain (`*`), the aliens' captain (`%`) and their ship (`+`) first, so `text.Contains( CommText( id ) )` misses a line that has one of them (the Thrynn greetings 380, 381 and 383, the Veloxi surrender 486), and a check on a randomly picked line then fails only sometimes. Match a line with `SaysLine`, or `SaysOneOf` / `SaysALineOf` / `SaysALineOfAnyStance`, which use it: it finds the pieces between the placeholders in order.
- **A scenario that changes scenes** works: the probe object is `DontDestroyOnLoad`. Wait with `WaitForScene`.
- The watchdog ends a run after 120 s, so keep the real-time waits of one scenario under about 60 s.
- **Lifeforms decide on the same frame, in no fixed order.** Every `TerrainLifeform` decides every half second from the frame it was placed, so they all decide together, in the order Unity updates them, and a lifeform may unpair at random (2% a decision) on the decision that pairs it. A scenario that needs one lifeform to react to what another does (a prey to a hunter coming at it) holds the first one's decisions (`m_behaviourTimer` set to 0.5 every frame) until the other is doing it, then sets its timer to 0 so that it decides on the next frame. No hunter approaches a lifeform in the air, and a flyer lands only now and then when it wanders (20% a decision) or when it attacks: a prey that took off may stay out of reach for seconds. A lifeform whose decisions are held keeps moving the way it last decided, so set its `m_moving` to false as well. A hunter left to decide while its prey is in the air wanders on (the test animals move 12 units a second) and can be out of the encounter area, where it does nothing, within seven seconds: hold it until the prey is down.
- **Never put a deposit inside the terrain vehicle.** Deposits push a terrain vehicle they touch (`TerrainVehicleCollider`), and now and then the vehicle keeps the push and drives off, out of reach of the deposit. The vehicle reaches 4.9 ahead of its middle and a deposit on planet 90 has a radius of up to 3.8, so a deposit in front of it is never both in reach (10) and clear of it: use `BesideTheVehicle`, which puts it 8 to the side.
- **A failed check is not always the change under test.** Missiles in flight survive the end of an encounter, so one fired in the last encounter can hit the player in the next. The `m12` scenario calls `ClearMissiles()` before it leaves an encounter for that reason. Read the log around a failure before blaming the change.
- **Hits damage the ship's systems, not only its armor.** Every hit that gets through the shields also takes a share of the ship's maximum armor (250 for a bare hull, whatever `m_armorPoints` is set to) from one installed system picked at random, so a scenario that lets aliens fire on the ship for a while may find the launcher, the lasers or the engines destroyed when it uses them next. `commlink` failed now and then that way. Call `ship.RestoreSystems()` (and reset the cooldown) right before the ship has to fire or fly.
- **A run writes one font asset again.** A run that shows the "Starport clear" message makes Unity write `Assets/TextMesh Pro/Resources/Fonts & Materials/LiberationSans SDF - Fallback.asset` again (the message has an arrow that only the dynamic fallback font can draw). The file is committed in the format Unity writes, and `.gitattributes` checks it out with LF line endings, so the run leaves the working tree clean. In a checkout made before that (CRLF in the working copy), `git status` lists the file as modified with an empty diff after such a run: `git checkout -- "<path>"` clears it. Stage files by name after a run in any case.
- **Console input without real input:** `SetInput( "m_south", true )` sets an `InputController` property by reflection, and `ConsoleFrameWith( "m_submit" )` runs one `ButtonController.Update` with it held. `InputController.Update` overwrites the property on the next frame, so set it and call the update in the same step.
- **Real key presses:** `HoldKeys( Key.Numpad8 )` holds keys of a virtual keyboard down (`HoldKeys()` lets them all go) from the next input update on, and `Tap( keys )` presses them for three frames. They go through the Input System to `InputController`, the UI input module and `Keyboard.current`, like a player's keys. `ProbeKeyboard()` adds the keyboard and sets the Input System's in-memory settings so that keys reach play mode without a focused game view. Anything that reacts to a key (the spaceflight controller opens the save panel on Escape, the console debounces) also does so here: switch it off for a check of `InputController` alone.

### Facts about the data that decide what is worth testing

- Hyperspace encounters show all their ships at once. The 128 star-system encounters have 6 ships, 3 at a time; those are the ones where a ship's index and its model slot drift apart.
- Only vessels 1 to 4 (Spemin, Mechan) and 20 have a debris model. Encounters 115 and 116 are Spemin, 7 is Elowan.
- Mechans are hostile to a ship with no human crew.
- Twelve encounters are in orbit around a planet (location 2). Star 30 has one of them (316, a derelict at planet 115) and no other encounter, which makes it the quiet place to test them. Since the encounter data was corrected to the original (2026-10-09) all twelve name an orbit that has a planet; before that 139, 165, 302 and 305 could never begin. Star 32 (82,148) has the Spemin home fleet and five Spemin star system groups.
- The Arth system (where a scenario starts) has four planets besides Arth: 90, 91 and 92 are frozen, 94 is a small rock planet. Planet 90 has a mineral density of 43% (762 deposits, 2218 cubic meters in all). Landing and disembarking work headless; the landing animation takes 35 s.
- A new game has 20.0 cubic meters of Endurium (200 tenths), 250 armor points and, in the Editor, 1,000,000 MU (a build starts with the original 12,000 MU; the probe always runs in the Editor).

## Limits

- No graphics. Anything visual has to be checked in the GUI Editor.
- It reports what the code does, not what a player sees, and it drives the game through its own methods. The `input` scenarios press keys of a virtual keyboard, which goes through the same Input System path as a real one but says nothing about how the controls feel.
