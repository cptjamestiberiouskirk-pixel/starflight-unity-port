# Changelog

All notable changes to the Starflight Unity Port will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- **A Livelier Starfield**: the stars of the spaceflight starfield (`InfiniteStarfield`, eight layers that wrap round the camera for parallax) were all alike within a layer, the same size and colour, drawn from 8 by 8 pixel sprites that show blocky when the camera is close. Each star now has a size and brightness of its own (many faint stars and few bright ones, as in a real sky) and a colour from blue white to orange, tinted by its layer; the brightest 3.5% have a short cross shaped glint, and nearly half of them twinkle gently, each at its own pace. They are drawn by a shader of their own (`Assets/Resources/Shaders/Starfield Star.shader`): a sharp core and a soft halo with no texture, the twinkle worked out on the graphics card from each particle's stable random numbers, so it costs nothing per frame on the CPU. The stars' new properties come from a random sequence of their own; the starfield still takes exactly four of the game's random numbers for each star, so nothing that draws from the game's random numbers afterwards is changed. The probe scenario `starfieldpictures` checks the sizes, colours, glints and twinkle (all four fail on the old code) and that the game's random numbers are drawn as before.
- **Compile Check CI**: `.github/workflows/compile-check.yml` runs a headless compile with the project's Unity version on every pull request and push to `master` using GameCI (`game-ci/unity-test-runner`, EditMode). Needs the `UNITY_EMAIL` and `UNITY_PASSWORD` repo secrets, plus `UNITY_SERIAL` (Pro/Student) or `UNITY_LICENSE` (Personal). Running it by hand (`workflow_dispatch`) takes an optional `unityVersion` to compile against a different editor. A final step lists any committed `Packages/` or `ProjectSettings/` files Unity rewrote during the run
- **Unity CLI Editor Bridge**: `com.unity.pipeline` 0.8.0-exp.1 (experimental) lets the Unity CLI drive an Editor that has the project open: `unity status` to see it, then `unity command console`, `recompile`, `editor_play`, `eval` and about 160 others. Tools such as Claude Code can read the console and check compiles through it. Its server listens on 127.0.0.1 only and needs a per-Editor token. It is compiled out of release builds, and in development builds it stays off unless switched on in its settings. Brings `com.unity.nuget.mono-cecil` back as a dependency
- **Headless Play-Mode Probe**: `DevTools/HeadlessProbe/` runs the real Spaceflight or Starport scene headless in play mode, with an in-memory save system so that no save file is touched, and checks game behaviour through scenarios, one for every fix made since 2026-10-03. A scenario starts once the planets of the first star system have been generated, because the game is paused until then. `probe.ps1` runs one scenario, `run-all-scenarios.ps1` runs them all and `compile-check.ps1` is the local compile check. The folder is outside `Assets/`, so it is not part of the build, and `.gitignore` keeps the copy that a run puts into `Assets/` from being committed
- **Shared Claude Code Settings**: `.claude/settings.json`, `.claude/rules/`, `.claude/agents/` and `.claude/skills/` are tracked now; worktrees, local settings and other local files under `.claude/` stay ignored. The settings deny edits to `Assets/Resources/Planets/` and `Assets/Planet Generator/Data/` (the planet generator tool writes them from inside Unity, which the rule does not touch) and ask before an edit to `Assets/Resources/Starflight Game Data.json`. The `headless-probe` skill calls the scripts in `DevTools/HeadlessProbe/` instead of keeping its own copies, and the probe README names the font asset a run can leave modified.
- **Path-Scoped Claude Code Rules**: five files under `.claude/rules/` (save serialization, the spaceflight loop, the ship console, the planet generator, panels and persistent objects) carry the CLAUDE.md rules for those areas and load only when a matching file is read or edited. CLAUDE.md still has the same text; it is trimmed in a later change.
- **Local Claude Code Settings in New Worktrees**: `.worktreeinclude` names `.claude/settings.local.json`, so Claude Code copies that ignored file from the main checkout into each worktree it creates. A new worktree starts with the same local settings as the main checkout, its permission rules included.
- **Encounters in Orbit**: the game data has twelve encounters that wait in orbit around a planet (home fleets, the Veloxi drones, a derelict), and nothing ever began them. An encounter in orbit now begins when the ship goes into orbit around its planet: the ship drops out of orbit into the encounter, the aliens come from the side of the planet, and when the player flies out of it the ship is back at the level of the star system, where it was before it went into orbit. That is the original design (`Research/Notes/gameflow.txt`). Going into orbit again begins it again for as long as it has living ships, and after a launch from the planet's surface it waits for the launch animation to end. The planet is not drawn in the encounter yet. **Data**: four of the twelve name an orbit that has no planet in the game data (encounters 139, 165, 302 and 305), so those four still cannot begin; the game data was not changed
- **The Planet Under an Encounter in Orbit**: an encounter that began in orbit was fought in empty space, though the ship had just gone into orbit around a planet. As the 1984 notes have it (`gameflow.txt`: "If an encounter occurs when a ship is in orbit the ship drops to a tactical map which has a planet in it ... Ships and weapons move OVER the planet, and it scrolls around and does not affect anything") and as ruling 5 left for a later step, the planet now lies under the encounter: the orbit view's sphere with the planet's own surface, as large as its mass makes it, below the ships and centred under the ship where the encounter began (`Encounter.ShowPlanetBackdrop`). The notes' planet was a disc of three sizes and six colours; the port draws the planet itself. How large and how deep below the ships are the port's. Checked with the `orbitplanet` probe scenario: a Spemin encounter met in hyperspace has no planet (the control), and the derelict in orbit 3 of star 30 is fought over its planet's own surface; the check fails on the code before. With `probe.ps1 -Graphics` it also renders the encounter into `Logs/orbit-encounter-pictures/`.
- **The Ancient Ruins STRINFO's Editors Place**: STRINFO's notes give three ancient ruins that hold only Endurium. One stands at 36N x 90E on planet 5 of 145,107, the Mechans' "ice planet in our system", with 3.1 cubic meters (2.1.4). Two stand at 42S x 13W on planet 2 of 154,62, deep in Elowan space where the Thrynn say "a fairly large ancient ruin" lies, with 3.1 and 5.9 cubic meters (2.5.4). The port had the alien lines that point to them but not the ruins. They are now records of their own in `Starflight Recovered Data.json` (`m_ancientRuinSiteList`, `GD_AncientRuinSite`), resolved with the other recovered records. `TerrainRuins` places them without random numbers, each holding its Endurium as a random ancient ruin holds its own (taken once). The Red Cylinder sees them, and their planets get no random ruins ("nothing else of note is there"). STRINFO puts the two Thrynn ruins at one place; the port puts the second 40 units east of the first. Found by the audit of the recovered texts against STRINFO (roadmap Phase 7). Checked with the `ancientsites` probe scenario: both checks fail on the code before and pass after.

- **The Notices Screen as the Original's**: the Operations notices screen said "Today is" and the date, ended a notice with nothing, and with no new notice showed the last one again without asking. [N Y]", repeating it after "***REPEATING LAST NOTICE***" on Y. `OperationsPanel` now does the same: the date beside the scene's Notices heading, the end line, and the question, which the screen's More and Quit answer as Yes and No (relabelled while it is asked); No goes back to the menu. The decompiled original does show it (ENGINEER, `(/REPAIR)`): Repair puts a cursor on the DAMAGE display, the stick moves it up and down the seven rows and the text window tells about the row under it ("ENGINES: SLIGHTLY DAMAGED", its efficiency, "CURRENT FUNCTIONALITY: OPERATIVE" or "INOPERATIVE", "ESTIMATED TIME FOR COMPLETE REPAIRS:" in minutes, hours or days, "CURRENTLY UNDER REPAIR.", "NONE" for what the ship lacks), and the fire button chooses: "NO REPAIRS NEEDED.", "DAMAGED BEYOND REPAIR." at 0, "ALREADY UNDERGOING REPAIRS.", "CEASE REPAIRS ON X AND BEGIN REPAIRS ON Y? - **The Bank Pays Its Interest**: the Bank screen says INTEREST RATE: 12% and the original's ledger has INTEREST rows, but nothing in the port paid any. The original (BANK-OV in the decompiled original, INT%) pays 12% a year of the balance for the days since it last paid, a year being the 300 days of its calendar, worked out as the balance times 12 over 100 and then times the days over 300, each rounded down; it pays when the crew goes aboard at the Starport (PORTMENU-OV, after the flight check) and on a new colony recommendation (CAPTAIN), and while the interest comes to less than 1 M.U. it pays nothing and the days count on. `PlayerData.PayInterest` does the same from the docking bay panel and the recommendation's Yes button, with an Interest row in the ledger; the day it was paid up to is saved in the bank (`PD_Bank.m_interestDay`), and a save file from before it starts counting the next time, with nothing paid for the days before. Found by the comparison of the screens (`Research/Screen comparison.md`, section 21), which now also records that the original books a recommendation's bonus or fine at once, where the port pays it on docking. Checked with the new `starport-interest` probe scenario (the rules, an old save, and the real docking bay: 100,000 M.U. for 150 days earn 6,000), which fails on the old code and passes on the new; `colonies`, `starport-ledger`, `starport-transport`, `starport-win`, `savedata` and `starport-savedata` pass.

The port's Damage wrote a "Damage Report:" text instead. `DamageDisplay` is that display, made at run time by `DisplayController` with the UI kit's styles (the scene has no object for it); Damage shows it and writes nothing, Repair shows it before the engineer speaks, and its bars follow the repairs under way. - **A Comparison of the Screens With the Original**: `Research/Screen comparison.md` records every difference found between the port's screens and the original's (roadmap Phase 7, the screens half), checked again on 2026-10-12 against the probe's new pictures of the flight screens and the Starport's rooms and against the decompiled original where the screenshots stop. One table per screen gives each item's status (fixed and by which PR, open, partly, not a defect, the owner's call, or a gap in the probe's pictures), its owner (the game logic or the UI kit) and its evidence. Of the 51 items of the game logic 22 are fixed and 25 are open, among them the DAMAGE display and Repair's choice of system, the bank's interest (the screen says 12% and nothing pays it), the notices screen, the combat messages and wounds, and MOTION DETECTED AT X: Y:; its Step 2 list orders them. - **An Audit of the Messages Against STRINFO**: `Research/STRINFO message audit.md` lists every place where a message the player sees differs from STRINFO (roadmap Phase 7): the comm lines, the notices, the evaluations, the Starport's analyses and prices, the ruin messages, the story texts, and the texts written in C#, each with the port's text, STRINFO's with its section and line, the file and line, and a category. The game data's comm lines are the shipped game's: in all 47 where STRINFO's words differ, the shipped game has the game data's. The game data's notices and analyses follow STRINFO where it departs from the shipped game, which is the owner's call. Its step 2 list records what the fixes since took (PRs 239, 243 and 246) and what is left; the Noah 9 beacon's lines turned out to be the shipped game's own phrases of the derelict, as the port has them.

(CAPTAIN overlay, `(/LOG-PLAN)`). The port now does both: `RecommendYesButton` takes the typed name on the console until Enter (Backspace takes a letter away; nothing is typed while the save panel is open; with no keyboard the planet goes unnamed) and says "Recommendation logged." where it said "Recommendation noted.", `PD_General.ColonyRecommendation` keeps the number, date and name (saved; a save file from before has none, and its pending recommendations get only the SYSTEM and ORBIT lines), and `PlayerData.EvaluateColonyRecommendations` puts the heading above each evaluation. Found by the audit of the messages against STRINFO (`Research/STRINFO message audit.md`, section 3). Checked with the `colonies` probe scenario: its three new checks (the question and "Recommendation logged.", Mardan 4's heading with NAME: NEW EDEN, a name cut to 15 characters and an empty one) fail on the old code and pass on the new; its four other checks, `savedata`, `starport-savedata`, `h7` and `starport-win` pass.
- **Veloxi Drones Grant Permission to Orbit**: the five Veloxi drone encounters guard their planets from orbit, and since in-orbit encounters began they stopped every landing there for good. As in the original (STRINFO 2.3), a drone now asks the player to confirm a series of numbers once the comm link is up: three numbers from 1 to 99, about half of them multiples of 6 (the number is not in the sources; the project owner chose three). A yes to each multiple of 6 and a no to every other number gets "Permission to orbit granted": the ship goes back into orbit and can land. The drone does not stop it again until it leaves the star system; on a later visit the drone asks again (the owner's choice; nothing new is saved). A wrong answer, or ending the comm link before the last number, gets "Permission to orbit denied", and the drone ends the comm link and attacks. The two lines are the first records of `Assets/Resources/Starflight Recovered Data.json`, a new file for what the original had and `Starflight Game Data.json` lacks, recovered from STRINFO (ids from 1000, each with its source). `DataController.LoadGameData` merges it into the game data (`GameData.AddRecoveredData`), so `Starflight Game Data.json` stays the original data. The comm subjects `OrbitGranted` and `OrbitDenied` are appended to `GD_Comm.Subject`. Checked with the `drones` probe scenario.

The ship now has one answer for the most armor and shield points it can have (`PD_PlayerShip.GetMaximumArmorPoints()` and `GetMaximumShieldPoints()`): the points of the installed armor, or the bare hull's 250. The damage text, both gauges, the Damage report and the Repair button all use it, the engineer repairs a bare hull ("Beginning repairs on the hull, Captain."), and the "Hull breach imminent" warning comes below a quarter of that maximum instead of below a fixed 250 points
- **Trade Depot Amount Parsing**: the decimal part was added as a raw integer (`5.25` became 7.5) and a lone `-` threw `FormatException`. Amounts are parsed as tenths with the invariant culture, accept a comma as the decimal point, and reject signs
- **Cargo Pods Could Be Sold From Under Their Cargo**: a cargo pod could be sold while the hold needed its space, leaving a negative free volume that the Trade Depot's "hold is full" check then missed. A pod can only be sold when the cargo fits without it ("Unload cargo first"), and the Trade Depot treats a negative free volume as full
- **Mineral Deposits Could Be Picked Up Twice**: a deposit stays on the surface for the 1.5 seconds of its transporter effect and could be picked up again during that time, so pressing Cargo twice put it in the hold twice. A deposit can be picked up only once now
- **Random Events Repeated After Every Trip in the Terrain Vehicle**: the rocks, deposits and trees of a planet are placed with random numbers that start from the planet's own seed, so that they are in the same places every time. That left the game's random numbers at the same point after every disembarking on the same planet, and everything random that followed (what the aliens say and do, where their ships appear) went the same way each time. The game's random numbers are put back where they were once the objects are placed
- **A Scan Counted a Deposit That Was Being Picked Up**: a deposit stays on the surface for the 1.5 seconds of its transporter effect. A scan in that time still listed it and put its label back up. A scan leaves it out now
- **Scan Labels Stayed After Leaving the Terrain Vehicle**: the labels a scan puts on rocks and deposits are not part of the objects they belong to, so they stayed in the air when the player went back into the ship, and their 30 seconds were no longer counted down. They are hidden with their objects now
- **Crater Maps Were Read Again on Every Start of the Spaceflight Scene**: three textures, about six million pixels, 0.45 seconds every time the scene started (coming back from Starport, after a game over). They are read once per session now
- **Displays Took Memory Every Frame**: the status display and the terrain vehicle display built their text from scratch every frame, a piece at a time, whether anything had changed or not. That took about 900 and 500 bytes a frame, which the garbage collector has to clear away again. The docking bay asked for the astronaut's materials nine times a frame while he faded out (about 570 bytes a frame). The texts are only built again when something they show changes now, and the materials are fetched once
- **Stardate Texts Were Made Every Frame**: the game time made its two stardate texts again in every frame of flight, 112 bytes of garbage a frame, although they only show the day and the hour. They are made when the day or the hour changes now, and once after a load
- **The Spaceflight Scene Stayed in Memory After It Was Left**: three things kept hold of it. The spaceflight controller's own static reference was never cleared, the save panel remembered who had opened it last, and the code that places rocks and deposits remembered the planet the terrain vehicle was last on. Through them every object of the scene and the height maps of its planets stayed in memory at Starport and on the title screen (about 40 MB in a test). All three let go now
- **Picked Up Deposits Left Their Materials Behind**: the transporter effect of a deposit that is picked up made its own copies of the deposit's materials, and one for its sparkles, and none of them were destroyed with the deposit: three materials for every deposit picked up, until the next change of scene. They are destroyed with the effect now
- **A Log Opened Scrolled to the Wrong Place After an Empty Log**: the ship's log kept the scroll position of the log it had shown before. Usually that was put right at once, but not when an empty log had been shown in between. Then the next log opened scrolled down, with its selected first entry out of sight, until the stick was moved. A log always opens at its first entry now
- **Ship's Log Scroll Loops Have a Limit**: the two loops that scroll the list of a log to its selected entry had no limit on their passes. Each pass scrolls one row, so they are limited to one pass more than the log has entries. The hang the review suspected does not happen in play (shown on 2026-10-04); with a state set by hand, a list that is scrolled down and rows of no height, the old loops never ended and the new ones end at once
- **An Object on the Very Edge of the Map Had No List to Go Into**: the placing of rocks, deposits and trees keeps lists of what is where, 32 of them across the map. A position exactly on the right edge of the map belonged to a 33rd list, which does not exist, and placing it failed. It takes the random number generator returning the largest number it can, so it is rare, and no planet is known to be affected. Such a position goes into the last list now
- **Cargo Volumes Were Shown Ten Times Too Large**: the cargo holds count in tenths of a cubic meter, and several texts printed that number as cubic meters. The ship's cargo list showed 200 for 20.0 cubic meters of Endurium, the terrain vehicle said "Picked up 3 cubic meters" for a deposit of 0.3, and its cargo list read "Capacity: 3/500 m³" for 0.3 of 50.0. They all show cubic meters now. What is picked up has not changed
- **A Deposit Too Large for the Hold Vanished**: when the terrain vehicle had room for only part of a deposit, it took that part and the whole deposit disappeared. The rest now stays on the ground, and the message says how much is left
- **Bank Ledger Showed Income as "-1400+"**: leaving the Trade Depot or Ship Configuration with more money than before wrote the amount with its minus sign and a plus behind it. It reads "1400+" now, as spending reads "500-"
- **Buy Maximum Overflowed Above 214 Million MU**: the Trade Depot worked out the most the player can afford by multiplying the balance by ten in 32 bits, so with 300,000,000 MU it came to a negative amount. It is worked out with 64 bits now
- **Sensor Analysis Said "0 times the size of our ship"**: the size of a scanned vessel is its mass divided by ours, and the division dropped everything after the point, so a vessel half our size was 0 times and one 8.9 times was 8. It has one decimal now
- **Garbled Alien Words Dropped**: 70445da left the capitalization `if` without a body, so it guarded adding the word and most garbled words disappeared from alien messages. The capitalization block is restored
- **Alien Messages Showed a `*` Where the Captain's Name Belongs**: the game data marks the captain's name with `*` and the ship's name with `&`. They were filled in for what the player transmits, but what the aliens say was built from the unfilled text again, so the Spemin asked about "the necessities of self defense captain *". Eight alien lines carry the captain's name and one the ship's name. They show the names now. The names of the alien captains and their ships (`%` and `+`, in 15 alien greetings) are still not filled in: the game has no names for them
- **Mechan 9 Could Be Unlocked After Firing on the Mechans**: five right answers to the Mechans' questions unlock Mechan 9 for good. That also worked in an encounter in which the player had fired on them. They stayed hostile, as aliens that have been fired on do until the player leaves, but every later Mechan encounter began friendly. Right answers no longer unlock Mechan 9 in an encounter in which the player has fired on the Mechans
- **A Button Press Could Land on Different Buttons**: the fire button activates the selected button 0.35 seconds after the press. If the buttons changed in that time, for example because the aliens asked a question, the press activated the first button of the new set. A press on Statement answered Yes to a question the player had not read yet. A press is dropped now when the button it was made on is no longer the selected one
- **Statement Button Could Transmit "ERROR"**: the game data has statements for the friendly, hostile and obsequious postures and none for the neutral one, so a statement in a neutral posture transmitted the word ERROR. Nothing is transmitted then. The console does not get there today (the comm buttons come after a hail, which sets a posture); this is a guard
- **Missile Immunity Never Loaded**: the game data key was spelled `m_immuneToMissles`, so `GD_Vessel.m_immuneToMissiles` was always false. The key is renamed (no values changed); Gazurtoid ships and the Mysterion are immune again
- **Missile Launchers Could Never Fire**: the missile count was only ever counted down. Nothing stocked it, so a bought launcher always answered "Out of missiles!". Missiles are no longer counted. Every launch uses 0.02 cubic meters of Endurium and every laser shot 0.01, and neither weapon fires with no Endurium on board
- **Most Alien Ships Scanned as "Unknown"**: the sensor display has no picture for 15 of the 23 vessel types, and when the picture was missing it also replaced the scan type with Unknown. Scanning an Elowan, Thrynn, Veloxi, Gazurtoid or Uhlek ship (or debris) showed "Unknown object detected" and the analysis said "Insufficient data". Now only the picture falls back to the unknown one; the readout and the analysis are for the real ship
- **Training Blocked Once Medicine Was Maxed**: the Train check compared only the last skill. It now compares the totals across all skills
- **Repair and Treat Were Instant and Free**: one press of Repair restored five armor points per point of engineering skill on the spot, and one press of Treat healed every hired person at once, including people who were left at Starport. Both take time now. The engineer repairs the armor at 0.02 points a second per point of skill (never less than 0.5), the doctor treats the most injured living crew member on board at the same rate, one patient per command, and both report when they are done. Pressing the button again shows the progress and the time left
- **Planet Gravity Lost a Zero**: gravity is stored in hundredths of a G, and the text dropped the leading zero of the fraction, so 105 read "1.5 G" instead of "1.05 G" and 5 read "0.5 G" instead of "0.05 G" (105 of the 811 planets). The fraction is always two digits now
- **Entering a Star System Froze the Game**: the maps of each planet are worked out on a background thread, but the main thread then waited for that thread to finish, so the game stood still for as long as each planet took and the "Commencing System Penetration" progress bar only moved once per planet. The main thread now looks each frame whether the planet is done and carries on when it is, so the game keeps running and the bar moves while a planet is being worked on
- **Planet Colours Were Blurred to One Side Only**: the filter that makes a planet's colour map softens it with a small blur, but a slip in the index meant every pixel took a quarter from its right neighbour and nothing from its left. It takes a quarter from each side now. A second blur, from row to row, built a 32 MB map for every planet and then threw it away; it is gone, and nothing it did was ever on screen. On planet 90 the fix changes 7% of the pixels, by 1.4 of 255 on average and by 64 of 255 at the most, at the edges between colours
- **Planet Generator Tool Padded the South Pole With the North Pole's Heights**: the tool adds rows above and below each planet's 24 rows of source data, and those rows blend to one height per pole. For the south pole it looked at the colours of the bottom row but took the heights from the top row. It reads the bottom row now. This only shows in planets that are generated again: the 811 planet files in the project were made with the old code and are not touched. For 273 of them the south pole would come out at a different height, by a fifth of the height range at the median
- **Planet Generator Tool Could Hang or Fill Planets With NaN**: an exception anywhere in the tool left its progress bar on screen, so the Editor looked as if it had hung (a wrong game data file name was enough). With Evaporation Constant at 0 a rain drop of the erosion pass took 25 times as long to end, and with Friction Constant at 0 as well it never ended. Mountain Scale or Lacunarity at 0, or a Final Blur Radius of 0, divided by zero and filled the height map with NaN. The tool now checks its settings before it starts and says what is wrong, always takes its progress bar away again, gives every drop a limit of steps (twice what its water can last), and treats a blur radius of 0 as no blur. Texture Map Height has to be 1024, the one size the game can read
- **Planet Generator Tool Gave a Different Planet Every Time**: the erosion pass rained on eight parts of the map at the same time, on eight threads that all wrote to the one map without a lock. A drop runs out of its own part, so now and then an update was lost: six runs on the same map gave six different results. The eight parts are rained on one after the other now, on one thread, so the same map and settings give the same result every time. The pass takes about five times as long (5.2 s for 1.0 s on a 256 by 128 map on a 16 processor machine). **No planet file was generated again**: the 811 files in the project are as they were
- **A Damaged Planet File Locked the Game**: when the data file of a planet could not be read (damaged, or made by another version of the planet generator), the error came back on the main thread every frame, so the game stayed paused in the middle of "Commencing System Penetration" for good. Entering the system had already saved the game, so loading the save led straight back into it. A file that was cut off inside its last part raised no error at all and left part of the planet's surface data empty. A planet whose file cannot be read is now skipped with an error in the log, and the other planets of the system are generated as usual. The reader checks the version, the size of the maps, that all of the data is there and nothing more, and the checksum of the file. All 811 planet files in the project pass it
- **Landing on a Planet That Could Not Be Generated**: when the maps of a planet cannot be generated (its data file is missing or damaged), the planet has no elevation data, and the Descend button ran into that with an exception after "Computing descent profile...". The Land button now refuses such a planet ("We can't land here. The surface of this planet could not be mapped."), and so does Disembark for a saved game that is already on its surface
- **A Planet That Could Not Be Generated Wore Another Planet's Maps**: when the maps of a planet cannot be generated (its data file is missing or damaged), the planet kept whatever was on its material, which is the maps of the planet that was in the same orbit in the star system before. It is shown as a plain grey ball now (four plain maps of 4 by 4 pixels, no surface detail), and the player is told "The surface of this planet could not be mapped." when the ship comes within orbital range and when it goes into orbit. Its clouds and atmosphere are still shown: they come from the game data, not from the file. **Not seen**: the probe has no graphics, so the look itself was not looked at
- **Planet Maps Were Never Freed**: every planet of a star system gets its texture maps made when the ship enters the system, and the maps of the system before were left in memory, with the planet files they were made from. Loading the next scene (docking at Starport) cleared most of them out, but not the maps of the last system. Flying through four systems took the textures made at runtime from 22 MB to 69 MB in a headless run, which has no graphics memory to count. The maps of a planet are now destroyed as soon as the maps of the planet that takes its place are on its model, or at once when its orbit is empty in the new system or the scene is left, and a planet file is unloaded as soon as its data has been copied
- **Raising Shields With No Fuel**: shields could be raised with no Endurium, then every game hour fuel use threw a NullReferenceException. Raising shields now requires Endurium
- **Lowering and Raising Shields Refilled Them**: lowering the shields threw their charge away and raising them set it to full, so two button presses in the middle of a fight restored the shields completely. The shields now keep their charge when they are lowered, only absorb damage while they are up, and regain 1% of their full charge every 5 seconds (the rate in the original design notes). Starport recharges them fully while the ship is docked. A save made with the shields down gets a full charge once
- **Progress Lost on Quit**: the game only saved on location changes and panel closes. It now also saves when the application quits, except when the ship has been destroyed
- **A Game Saved in the Terrain Vehicle Loaded Into Starport**: the game saves when the terrain vehicle is entered, but the list that says which scene a saved game belongs to did not know that location, so continuing such a game opened the Starport scene. It opens the Spaceflight scene now. The save panel did not know the location either and ran the ship's line into the location line; it says "Terrain Vehicle" now
- **A Game Saved in the Terrain Vehicle Was Stuck When Its Planet File Broke**: a game saved in the terrain vehicle and loaded after the planet's data file was damaged had no ground to drive on, no way back to the ship, and threw an exception on every frame (61 in the first second). Such a game now goes back into orbit when it is loaded: the terrain vehicle comes on board with its cargo, the ship is put in orbit, the game is saved there, and the player is told why
- **Stardate Depended on the Computer's Calendar**: the stardate text was made with the calendar of the computer's region. On a computer set to the Thai calendar the year read 5163 in place of 4620, and on one set to the Saudi Arabian calendar, which has no year 4620, working out the game time failed on every frame of spaceflight. The stardate is always made with the same calendar now
- **Bank and Notice Dates Depended on the Computer's Region**: the bank's date column, "Today is" and the date of each notice in Operations, and the date and heading a notice gets in the ship's log were written with the date format of the computer's region, so the Thai calendar showed the year 5163 and every region had its own order of day and month. These are stardates, and they are shown as the game shows stardates now: day-month-year, `26-03-4620`, as on the original game's bank and notice screens (`PD_General.GetDisplayStardate`). The ship's log keeps its entries in the save, so notices that an older build dated are dated again when the save is loaded
- **New Game Terrain Vehicle Was Never Set Up**: a new game made its terrain vehicle but did not reset it, so it started with no fuel and no cargo holds, and only worked because disembarking refuels it and the first pickup makes the hold. A new game resets it like everything else now
- **Game Over Put You Back in the Lost Fight**: after the ship was destroyed, returning to the title screen kept the lost game in memory, so continuing dropped the player into the same encounter with no armor and the aliens still hostile, and closing the save panel while the ship was exploding wrote the destroyed ship to the slot. The title screen now reloads the slot from its last save (the one made when the encounter began), and a destroyed ship is never saved, copied to another slot or carried through a slot switch. A save that an older build wrote with a destroyed ship loads with 1 armor point so that it can be saved again
- **A Crash While Saving Could Wipe the Slot**: saves were written straight over the old file, and a save that could not be read was silently replaced by a new game and then overwritten. A save is now written to a temporary file and swapped in, the save it replaces is kept as `.bak`, loading falls back to that backup, and a save that can't be read is moved to `.corrupt` so nothing overwrites it
- **Debris and Missiles Used the Wrong Alien Ship Model**: combat used a ship's position in the encounter's ship list as its model slot, but the model slots are packed so that only living ships get one. After leaving and re-entering an encounter with ships already destroyed, a kill spawned its debris into another ship's slot or an empty one, and an empty slot made `Encounter.Update` throw every frame so the player could not leave. `Encounter` now keeps a ship-to-slot map behind `GetAlienShipModel()`, used for debris and for missile homing
- **Aliens Never Fought Back**: only the Mechans ever turned hostile, firing on a ship changed nothing, and the Uhlek had no update at all, so their 67 encounters never acted. Firing a laser or launching a missile at any alien now makes that encounter hostile until the player leaves it, the Uhlek attack on sight and never talk, and a race with no update of its own (the Enterprise) shoots back once it has been fired on
- **Aliens Kept Firing During a Comm Link**: hostile aliens went on shooting at the ship while the comm screen was up and the two sides were talking. They hold their fire for as long as the link is up now, and the time to their next shot does not run down while they talk; when the link ends the fight goes on. This is the original design: every alien fire rule in the design notes requires `?IN-COMM FALSE` (`Research/Notes/communic.txt`). The check sits in `Encounter.UpdateAlienCombat`, the one place all alien fire comes through, so it holds for every race
- **Destroyed Ships Kept Flying**: a destroyed ship was still moved every frame, so its wreckage chased the player. Only vessels 1 to 4 and 20 have a debris model, so destroyed Elowan, Thrynn, Veloxi, Gazurtoid and Uhlek ships kept their normal model as well and looked alive. Destroyed ships now stay where they died, a ship with no debris model disappears with its explosion, and the encounter camera only keeps living ships in view
- **Combat Target Carried Over Between Encounters**: the selected target was never cleared, so a target picked in one encounter was still set in the next one, and firing only checked that the index was in range. A stale target could be a ship that was dead or not in the encounter yet, so the player could destroy a ship that was not on screen. The target is now cleared whenever an encounter is entered, and firing at a target that is not a living ship in the encounter clears it and says so
- **Unity Object Checks That Missed Destroyed Objects**: four places tested Unity objects with `??` or `?.`, which do not see that an object has been destroyed (the Target button, the F10 debug key, and the mineral and artifact pickups), and the terrain vehicle's collider compared tags with `==` and read the first contact point of a collision without checking that there was one. They use `== null`, `CompareTag` and a contact count check now, as the project rules ask. Nothing a player could see changes
- **Missiles Carried Over Between Encounters**: a missile still in the air when the player left an encounter kept flying and still did its damage when it arrived. An alien missile could hit the player in the next encounter, and a player missile damaged the ship with the same number in the next encounter. Every missile is now taken out of the air when an encounter ends and when one begins
- **Ship Could Be Destroyed More Than Once**: a hit on a ship that was already exploding destroyed it again, with another wreck, another explosion and another call of the game over screen. The aliens' own fire did this during the 1.5 seconds of the explosion. The ship is destroyed once now: missiles in the air are taken out when it goes, the aliens stop firing at the wreck, and the weapons of a destroyed ship do not fire
- **Missiles Kept Flying While the Game Was Paused**: a missile in the air flew on behind the save panel, the starmap and the ship's log, and did its damage there. Missiles stand still while the game is paused now and fly on afterwards
- **A Missile That Ran Out of Time Just Vanished**: a missile that had not reached its target after five seconds was switched off without a word. It now reports a miss to whoever launched it, as the code that handles the report always expected: a small explosion where the missile was, its sound, and no damage. This holds for the player's missiles and for the aliens'
- **Explosions Stayed at Half Size**: a missile hit plays its explosion at half size, and the explosion kept that size when it was used again, so the next ship to be destroyed could go up in a half-size explosion. Every explosion starts at full size now
- **A Launch With Every Missile in the Air Cost Fuel and Launched Nothing**: only eight missiles can be in the air at once, the aliens' included. With all eight in the air a launch still used its Endurium, made the aliens hostile and said "Missile launched!", but nothing was launched. Such a launch does nothing and costs nothing now
- **Alien Ships Had No Hit Points**: damage to an alien ship was worked out from scratch on every hit and never stored, so a hit either destroyed the ship outright or did nothing at all (a class 1 laser could never destroy a Spemin Warship, and one-shot an Elowan). Alien ships now have armor and shield points, 100 per class of their vessel, saved with the game. Shields absorb damage first. Ships in older saves get their points on the first hit
