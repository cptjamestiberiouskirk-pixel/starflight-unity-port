# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Unity 6 (**6000.3.13f1**) port of the 1986 space RPG *Starflight*. All gameplay C# lives in `Assets/Scripts/`. The game code has **no assembly definitions** (everything compiles into `Assembly-CSharp` / `Assembly-CSharp-Editor`) and there are **no automated tests**. The one exception is the optional AI tooling in `Assets/Scripts/AI/` (`Starflight.AI`, `Starflight.AI.Editor`, see "AI orchestration" below).

The 270 stars / ~811 planets are fixed data from the original game, not random generation: preserve original values when touching game data.

## Commands

The project is normally driven from the Unity Editor. Press Play in **any** of the four build scenes (`Persistent`, `Intro`, `Starport`, `Spaceflight` in `Assets/Scenes/`): see "Scene bootstrap" below.

Headless compile check (fails if the project is already open in an Editor; a fresh worktree has no `Library/` so the first run does a full import and is slow):

```bash
"/c/Program Files/Unity/Hub/Editor/6000.3.13f1/Editor/Unity.exe" -batchmode -nographics -quit -projectPath . -logFile -
```

CI runs the same compile check headless on every PR and push to `master` (`.github/workflows/compile-check.yml`, GameCI EditMode test run; needs `UNITY_EMAIL`, `UNITY_PASSWORD`, and either `UNITY_SERIAL` (Pro/Student) or `UNITY_LICENSE` (Personal `.ulf` contents) as repo secrets).

**Headless play-mode probe:** `DevTools/HeadlessProbe/` (outside `Assets/`, not part of the build) runs the real Spaceflight or Starport scene headless in play mode, with an in-memory save system so no save file is touched, and checks behaviour through scenarios. From the project root in PowerShell: `& "DevTools\HeadlessProbe\compile-check.ps1"` is the compile check above with a summary, `& "DevTools\HeadlessProbe\probe.ps1" -Scenario <name>` runs one scenario and `& "DevTools\HeadlessProbe\run-all-scenarios.ps1"` runs them all. For a gameplay fix, run its scenario on the old code and on the new code, and add the scenario in the same PR. A scenario that has to pass on the new code must be seen to fail on the old code first. Its `README.md` lists the scenarios, the helpers and the pitfalls. Stage files by name after a run. At the end of a series of PRs run all scenarios on the final tree: the few that are run with each PR are picked by what the change is thought to touch, and that pick can miss one.

`com.unity.test-framework` is installed but no test assemblies exist. If tests are added (they will need an `.asmdef` referencing the test framework), run them with `-runTests -testPlatform EditMode -testResults results.xml` and narrow to one test with `-testFilter <FullyQualifiedName>` (omit `-quit`).

Editor tooling is under the **`Starflight Remake/`** menu (`Assets/Tools/Editor/`, `Assets/Planet Generator/Editor/`).

Root-level asset scripts (not part of the Unity build): `process_ship_debris.py` is a Blender script (`blender --background --python process_ship_debris.py -- --help`); `process_texture_debris.py` uses Pillow (`python process_texture_debris.py --help`).

**Editor bridge:** the `com.unity.pipeline` package (0.8.0-exp.1, experimental; that is the package version, not the version of the Unity CLI) is installed, so the Unity CLI can drive an Editor that has this project open. The commands useful here are `unity command console`, `recompile` / `recompile_status`, `editor_play` / `editor_stop`, `eval` (C# against the project's assemblies) and `run_tests`. The server only listens on 127.0.0.1 and does not load while the Editor is in Safe Mode, so a failed connection can mean compile errors. Stop a headless Editor started for a worktree by its PID: `unity command quit` fails outside play mode in this package version.
## Architecture

Five path-scoped rule files in `.claude/rules/` hold the rules for parts of the code: `save-serialization.md`, `spaceflight-loop.md`, `ship-console.md`, `planet-generator.md` and `persistent-objects.md`. Each one loads when a file that matches its `paths` is read, written or edited.

### Scene bootstrap and singletons
`Persistent.unity` (build index 0) holds the `DontDestroyOnLoad` managers: `DataController`, `PanelController`, `InputController`, `SoundController`, `MusicController`, `SceneFadeController`, `PopupController` (all in `Scripts/Persistent/`). `DataController.Start()` loads game data and all save slots, then loads `DataController.m_sceneToLoad`.

Each scene controller (`IntroController`, `StarportController`, `SpaceflightController`) checks `DataController.m_instance == null` in `Awake()`; if so it sets `m_sceneToLoad` to itself and loads `Persistent` first. Code in `Start()` can therefore assume the persistent singletons exist. Singletons expose `public static X m_instance` assigned in `Awake()` (`SpaceflightController` assigns it in its constructor, and clears it in `OnDestroy` so that the scene does not stay in memory: it is null in the other scenes, and code that can run there has to check it).

### Two data layers
- **GameData** (`Scripts/Game Data/`, `GD_*` classes): immutable definitions parsed with `JsonUtility` from `Assets/Resources/Starflight Game Data.json`, then post-processed by `GameData.Initialize()`. Access via `DataController.m_instance.m_gameData`. That file stays the original data: what the original had and it lacks, recovered from STRINFO, goes into `Assets/Resources/Starflight Recovered Data.json` (`RecoveredData`: comms with ids from 1000, planet messages, artifact sites, colony evaluations and story texts, an `m_source` per record), which `DataController.LoadGameData` merges in before `Initialize()`. Its records name a planet as STRINFO does, by the star's coordinates and the planet's number counted from the sun; `GameData.Initialize` resolves them (`FindPlanetFromSun`).
- **PlayerData** (`Scripts/Player Data/`, `PD_*` classes): save state. Access via `DataController.m_instance.m_playerData`. Each `PD_*` has a `Reset()` that builds new-game state (and reads GameData, so DataController must exist).

Saves go through `ISaveSystem` → `JsonSaveSystem`, writing `Application.persistentDataPath/{fileName}{slot}.json` (5 slots) with **`JsonUtility`**. A save is written to `.tmp` and swapped in, the save it replaces is kept as `.bak`, loading falls back to the backup, and a save that can't be read is moved to `.corrupt`. `JsonSaveSystem` takes an optional directory, so it can be exercised away from the real saves.
- `Radar` sorts `PlayerData.m_encounterList` by distance every frame, so never index it by encounter id; use `PlayerData.FindEncounter()`.
- A destroyed ship (its hull's integrity at 0, `PD_PlayerShip.IsDestroyed`; a ship with no armor left is not destroyed) is never saved: `DataController.SavePlayerData` refuses it, and game over reloads the active slot from its last save (`ReloadActiveGame`). Nothing may bring the hull of a destroyed ship back above 0 (see the guard in `PD_PlayerShip.UpdateRepairs`), or the lost game becomes saveable again. The one exception is the repair in `DataController.LoadPlayerData`, which gives the hull of a save written with a destroyed ship 1 point of integrity when it is loaded.
- `DataController.LoadPlayerData` is where a loaded save is repaired (crew roles, a destroyed ship, armor points above what the ship can have, the dates of ship's log notices). A new repair goes next to those, and none of them may add armor points (the one for a destroyed ship gives its hull 1 point of integrity; armor below 0 in an old save becomes 0).
- Stardates are stored year-month-day (`m_currentStardateYMD`, the bank ledger, the notices) because that form sorts. Stardates are in the original's calendar of 10 months of 30 days, day 0 = 01-01-4620: make one from the day count with `PD_General.GetStardateYMD` or `GetStardateDHMY` and show one with `PD_General.GetDisplayStardate` (day-month-year), never with `DateTime` or the date formats of the computer's region.
- A build starts a new game with the original 12,000 MU, the Editor with 1,000,000 (`PD_Bank.GetStartingBalance`).

### Location state machine
`PD_General.Location` (`Starport, DockingBay, JustLaunched, StarSystem, Hyperspace, InOrbit, Planetside, Encounter, Disembarked`) drives everything. `DataController.GetCurrentSceneName()` maps `Starport` → Starport scene, everything else → Spaceflight scene.

Inside Spaceflight, `SpaceflightController.SwitchLocation()` hides every location then shows one. Each location is a MonoBehaviour in `Spaceflight/Locations/` with `Show()`/`Hide()` that toggle its GameObject. Changing location auto-saves. `SpaceflightController.Update` also ticks the background work that is kept in the player data: shield recharge, armor repairs and medical treatment (`PD_PlayerShip.UpdateShields` and `UpdateRepairs`, `PD_CrewAssignment.UpdateTreatment`), and the game clock (`PD_General.UpdateGameTime`, which also takes the shields' fuel every star hour; a star hour every 10 seconds of play, the original's REAL-MS). The clock runs in every location except the docking bay, as the original's clock, repairs and treatment run together.

`SpaceflightController.UpdateEncounters` moves the alien groups and begins encounters. The star system and hyperspace locations call it; it does nothing for any other location (a ship that has `JustLaunched` has the star system on screen but has not entered it), and it begins at most one encounter per frame, the nearest, and none for a minute after an encounter in flight has ended (`SpaceflightController.HoldOffEncounters`, called by `Encounter.LeaveEncounter`; the original's ENC-TIME).

An encounter in orbit (location 2 in the game data) is not met in flight. It begins when the ship goes into orbit around its planet: `InOrbit` calls `SpaceflightController.BeginInOrbitEncounter()` once per entry into orbit, and not while a launch or landing animation plays. `Encounter.LeaveEncounter()` is the one way out of every encounter: back to hyperspace or the star system, and for an encounter that began in orbit to the star system, never back into orbit (that would begin it again at once). The one exception is an encounter that has let the ship into orbit (a Veloxi drone answered correctly, `SpaceflightController.GrantOrbitPermission`): the ship goes back into orbit, and the encounter does not begin again until the ship goes to hyperspace. The permission is saved (`PD_General.m_orbitPermissionList`, read through `GetOrbitPermissions`, since older saves have none).

In the Spaceflight scene the Cancel input (the Escape key) opens the save panel, except during a launch or landing animation (`PlayerCamera.IsLaunchingOrLanding()`) and once the ship has been destroyed (`CombatController.PlayerIsDestroyed()`). A game that is over stays paused.

### Ship console (Spaceflight UI)
- `ShipButton` (`Spaceflight/Buttons/`) is a **plain C# class, not a MonoBehaviour** (`GetLabel()`, `Execute()`, `Update()`). `ButtonController.Awake()` instantiates every button into sets keyed by the `ButtonSet` enum (max 6 per set). To add a button, subclass `ShipButton` and add it to a set there; to add a menu, add a `ButtonSet` value before `Count`. `Execute()` typically calls `SpaceflightController.m_instance.m_buttonController.ChangeButtonSet(...)`. The fire button activates the selected button 0.35 s after the press, and only if the button the press was made on is still the selected one: the buttons can change in between (an alien question puts Yes and No on the console).
- Displays (`Spaceflight/Displays/`) subclass `ShipDisplay` and are switched by `DisplayController`.

### UI kit colour schemes
- The UI kit's colours come from a theme (`UIKitTheme`): fifteen schemes (`UIKitTheme.c_schemes`), each a dark and a light theme asset (`Resources/UI Kit Theme*`, `Resources/UI Kit Themes/`, made by `DevTools/UIKitSchemes/make_themes.py`), picked by the player on the save panel's Colors screen. Take colours from `UIKitTheme.Get()` or a `UIKitStyle` role, never hard-coded, and react to `UIKitTheme.Changed`.
- The scenes are saved in the classic dark theme's colours; `UIKitModeApplier` maps them to the theme in use by matching those colours, so a colour copied into a scene must be one of the classic dark theme's.
- Anything drawn over a 3D view (in the main viewport, under the object with `Viewport`; the Starport's door name, under a `UIKitOverView`; and the labels on the terrain) uses `UIKitTheme.GetViewTheme()`, the scheme's dark theme in either mode: `UIKitStyle` and the applier do this by themselves for what is under a `Viewport` or a `UIKitOverView` (`UIKitTheme.IsOverView`); code that colours such things itself calls `GetViewTheme()`. A new label over a 3D view outside the viewport gets a `UIKitOverView`, or the light modes draw it in dark text on the dark view.
- The Starport station's and the docking bay's materials (`Assets/Game Objects/Starport/`, `Assets/Game Objects/Docking Bay/`) keep the classic dark theme's colours; `StarportColours` gives them the view theme's at run time with a property block per renderer and material (the floor and the bay's doors through palette weights, `SF_PALETTEMAP_ON`), and in the Starflight and Starflight 2 schemes the 1986 Starport's EGA colours and the bay's colours from before the kit. A renderer whose colours an animation sets (the bay's sirens) takes them in the renderer's own block, since a block for one of its materials hides the animated values. A material that should follow the scheme goes into its table, which `UIKitConcourseTool` and `UIKitDockingBayTool` also read.

### Starport panels
`Panel` (`Scripts/Panel/`) is an abstract MonoBehaviour opened/closed via an `Animator` bool `"Open"`; the animation fires `PanelAnimationCallback` → `PanelController.Opened()/Closed()`. `AstronautController` opens panels when the astronaut enters a door.

### Input
Active Input Handling is "Input System Package (New)": the legacy `Input` class throws at run time, so never call it. `InputController` reads the Ship map of `Assets/Input/Starflight Input.inputactions` (assigned on it in `Persistent.unity`): ten button actions (`N`, `NE`, … `NW`, `Submit`, `Cancel`) on the keys the old Input Manager axes had. The UI map of the same asset drives the `InputSystemUIInputModule` of the Starport and Spaceflight event systems; a new scene with UI needs that module, not `StandaloneInputModule`. Code that reads a key directly uses `Keyboard.current`, which is null on a computer without a keyboard and in a headless run. Call `InputController.m_instance.Debounce()` after consuming a press. Editor-only debug keys in `SpaceflightController.Update()`: **F9** spawns a hostile Spemin encounter, **F10** destroys the player ship.

### Planet rendering
- **Production path**: `Planet` component → `PlanetGenerator` (`Scripts/Planet Generator/`) loads `Resources/Planets/{id}.bytes` asynchronously, decompresses on `Task.Run`, then runs `PG_*` filters (scale, blur, craters, albedo, specular, normal, water mask) as a step machine; `Process()` returns progress and is pumped from `SpaceflightController.Update()` while the "Commencing System Penetration" popup shows. Two rules it relies on:
  - An aborted planet has no maps and no elevation data: check `Planet.HasMaps()` before using its generator (Land and Disembark refuse such a planet). It is shown with four plain placeholder maps, which are a look and not data, and `Planet.CouldNotBeMapped()` is the question to ask once generation has ended (`HasMaps()` is also false while the maps are still being made). A game that is loaded in the terrain vehicle on such a planet goes back into orbit (`Disembarked.ReturnToOrbit`).
  - The textures a generator makes are never freed by Unity. `Planet` keeps the generator whose maps are on its material and calls `PlanetGenerator.Release()` once the next planet's maps are on it, when the orbit is empty in the new system, and in `OnDestroy`.
- **Objects on the surface**: `TerrainGridPopulator` places a planet's rocks, deposits and trees with `Random` seeded from the planet, so that they are in the same places every time, and puts the game's `Random.state` back afterwards. The objects are placed again every time the terrain vehicle goes out, so what has been taken from a planet is saved (`PD_PlanetSurfaces`: a deposit is known by its planet and the order it is placed in) and applied after the object's random draws. Anything else that needs repeatable random numbers has to do the same. A random ruin's draws are all made in `TerrainRuins.MakeRandomRuins`, which the Red Cylinder replays from orbit (`GetRandomRuinPlaces`, seeded with `TerrainGrid.GetRuinSeed`): a random draw added before the random ruins in `TerrainRuins.Initialize` would put them somewhere other than where the cylinder finds them. The number of random draws per object is part of every planet: a deposit's size (1.0 to 9.9 cubic meters as the original's SEED-OV draws it, kept in tenths like everything in the cargo holds) comes from its one draw, and a second draw would move everything placed after it. `PG_Craters.Initialize` reads the crater textures once per session, and with `GetPixel` on purpose: `GetPixels` gives values that differ in the last bit for these 16 bit textures, and every planet is worked out from them.
- **Experimental path**: `PlanetManager` + Burst `TerrainJob` + `PlanetData` ScriptableObject (`Spaceflight/PlanetGenerator/`), bridged by `ProceduralAdapter` (kill switch `ProceduralAdapter.EnableProceduralGeneration`).

### AI orchestration (optional)
`Assets/Scripts/AI/` builds a Semantic Kernel (`MetagameOrchestrator`) whose chat service (`ClaudeCliChatService`) runs `claude -p` with the prompt on standard input, never on the command line, and does the function calling itself: the offered kernel functions go into the system prompt, `--json-schema` makes Claude answer with either a final text or tool calls, and the service invokes the calls and loops (bounded by `m_maximumToolRounds`). Kernel functions run on thread pool threads, so they reach Unity only through `MainThreadDispatcher.Enqueue`.
- The packages come from NuGetForUnity (`Assets/packages.config`, `Assets/NuGet.config` with `slimRestore` off so that dependencies are restored). Both asmdefs require the `STARFLIGHT_SEMANTIC_KERNEL` define, which `SemanticKernelDefineSync` (`Assets/Tools/Editor/`) sets only while the Semantic Kernel DLLs are in `Assets/Packages/`. Never commit the define without those DLLs: CI would fail to compile.
- Game code must not depend on `Starflight.AI` (it is not auto-referenced, and it does not exist without the define).

### Coordinates
`Tools` (`Scripts/Misc/Tools.cs`) converts between original game coordinates (0–255 grid) and world space (`(game - 128) * 256`), plus lat/long and map conversions for planet surfaces. `Notes.txt` documents original-game constants (comm subject IDs, stance values, landing sequence, disembark move scale).

### Combat and encounters
`CombatController` (Spaceflight scene singleton) owns weapon cooldowns, damage (shields, armor, then the hull, the systems and the crew), and object pools for lasers, missiles, and hit/explosion effects. `Encounter.cs` (~2,000 lines) runs alien AI, comms, stance, and calls into `CombatController`.

Combat rules:
- Alien ships have saved armor and shield points, those of their vessel in the game data (`GD_Vessel.m_armor`, `m_shields`; `PD_AlienShip.ResetHitPoints`), and move at a speed that follows the vessel's move delay (`GD_Vessel.GetSpeedFactor`). A hit goes all to the shields if they have points left, are up (`Encounter.AliensHaveShieldsUp`) and the fight is not in a nebula, never below 0 and nothing over on to the armor; otherwise all to the armor (the original's DAMAGE-OV `WF162`). The Rod Device cuts an alien laser hit to a quarter (`WED36`).
- Firing on any alien calls `Encounter.PlayerAttacked()`, which keeps that encounter hostile until the player leaves it (`PD_Encounter.m_attackedByPlayer`), and silent unless the aliens turn cowardly (`Encounter.AliensAreFighting`, the original's COMM-OV `<TALK>`): they neither hail nor answer a hail, and a comm link that is up ends. The Uhlek are hostile on sight and never talk: the game data has no comm lines for them.
- An alien ship fires its laser and launches its missile each on its own, while fewer than 10 alien missiles are in the air, and an alien missile flies to where the player's ship was at launch (only a plasma bolt follows the ship), hitting it if the ship is still within 100 units of that place (`CombatController.AlienFiresAtPlayer`, the original's COMBAT-OV `<COMBAT>` and `WE929`).
- Alien fire is only reached through the race switch in `Encounter.Update`. A race without its own case gets the `default` case, which only shoots back. All of it ends in `Encounter.UpdateAlienCombat`, and the aliens hold their fire there for as long as the comm link is up.
- Player weapons have no ammunition. Every shot uses Endurium through `PD_PlayerShip.UseUpFuel` and needs `HasFuel()`.
- Shields keep their charge when lowered and recharge slowly. Repair and Treat start work that takes time; the buttons do not change the hull, the systems or vitality themselves.
- A hit on the player ship is the original's DAMAGE-OV (`CombatController.ApplyDamageToPlayer`): it lands in chunks, each a random share of what is left of it and at least 10 points, and each chunk on one thing: the shields while they are up (raised, charged, outside a nebula), else the armor while it has points, else one of the ship's working parts chosen at random (the hull, a system or the crew), which loses 10 times the chunk over the hull's integrity. Shields and armor lose (6 - class) / 5 of a chunk, and shields pass nothing on to the armor. The ship is destroyed when its hull's integrity (`PD_PlayerShip.ShipSystem.Hull`, saved with the systems: save files from before it have a whole hull) reaches 0, not its armor. The engineer repairs the hull and the systems, never the armor, which only the Starport restores; the status display's damage reads the hull and the systems (`GetOverallIntegrity`).
- The weapons do the original's damage (`CombatController.GetLaserDamage`, `GetMissileDamage`, `GetAlienLaserDamage`): LDAMAGE and MDAMAGE by class for the player and the aliens alike, a laser's falling off by a tenth a cell to nothing at 10 cells (`CombatController.c_unitsPerCell` is 80: the port's laser range of 800 is the original's 10 cells), an alien laser twice that (a quarter first with the Rod Device), the plasma bolt 4000 (a missile that follows the ship and hits when it arrives, one of the aliens' missiles in the air). Aliens fire only within 5 cells across and along (`Encounter.IsWithinWeaponsReach`); `c_alienFireRange` only frames the camera.
- A player's shot goes where the navigator aims it (`CombatController.RollAimOffset`, COMBAT-OV WF0D8): off target by whole cells unless a roll under 250 less the navigation skill comes under 50, so on target with (50 / (250 - skill)) squared, always from skill 200; off target a laser misses, and a missile flies to that place and misses. A laser shot burns 0.1 m³ of Endurium and a missile 0.5 (`UseUpFuel` takes every whole tenth at once). The probe's `EnsureCrew` has a navigator of skill 250, so that its shots hit.
- The most armor and shield points the player ship can have come from `PD_PlayerShip.GetMaximumArmorPoints()` and `GetMaximumShieldPoints()`: the points of the installed equipment, or the bare hull's 250 with no armor plating (`HasArmorPlating()`). Displays, the engineering buttons, repairs and the hull breach warning all use them; never hard-code a maximum. Armor bought onto a damaged hull counts a lower class than it has points for (`PD_PlayerShip.InstallArmor`, the original's armor class equivalency), so the armor points can be up to 249 over that maximum until the next Starport repair.
- An encounter forgets the combat target when it begins, and takes every missile out of the air when it begins and when it ends (`CombatController.ClearMissiles`). The other pooled effects are left to finish: the explosion of the player ship is what calls the game over screen.
- The player ship is destroyed once. From then on `CombatController.PlayerIsDestroyed()` is true: `ApplyDamageToPlayer` and `AlienFiresAtPlayer` do nothing, and the player's weapons do not fire. An explosion calls its callback after 1.5 s and is switched off after 2.2 s, when its particles are gone; `GetAvailableExplosion` hands it out at full size. A missile stands still while the game is paused, and one that runs out of time calls its callback with a miss (an explosion, no damage). A player launch that finds no free missile in the pool does nothing: no fuel, no `PlayerAttacked()`.
- A home fleet (an encounter met in orbit around its race's homeworld, STRINFO 5.2, `GameData.IsHomeworldOf`: the Spemin, Thrynn, Veloxi and Gazurtoid fleets 139, 165, 233 and 65) says only its homeworld lines (`GD_Comm.m_homeworld`, set from the shipped game's context of each line where PR 259's recovered postures have it: the lines it says only at a homeworld), each list (hails, responses, refusals) in the order of the game data and one step further each time it is used (`Encounter.FindHomeworldWarning`), a subject with no homeworld line answered from the refusals, asks no questions, and ends the comm link and attacks after the last line of a list.
- The Spemin, Thrynn and Veloxi turn cowardly once they have lost half of the ships that have come into the encounter (`Encounter.UpdateCowardice`, `PD_Encounter.m_aliensAreCowardly`): their stance is obsequious from then on, even if the player fires again, and only cowardly aliens say the game data's surrender lines, each of them first.
- The Elowan, Thrynn, Spemin and Veloxi (and the Mechans and Gazurtoid, below and in `AlienPersonality`) have a mood (`AlienPersonality`, `PD_Encounter.m_mood`, the draft's EDL): it picks the posture of their lines (`Encounter.GetAlienTalkStance`), and their stance is never Hostile from the mood except when they are too agitated to talk and fight, so a hostile posture is abusive talk without an attack. Whether a hostile band threatens or grovels, and whether fight or flight is fight, is the shipped game's strength rule (`Encounter.GetStrengthDifferential`: the ship's equipment classes and the captain's skills against the vessels' strengths of the recovered data). What moves the mood is the shipped game's (COMM-OV <EDL>): the player's shields and weapons, hails and replies, statements and questions by the phrases of the comm link, the aliens' unanswered hails, their lines' actions and the answers to their questions. The rules of the bullets above (fired on, cowardly, a home fleet, Elan, a refused demand) override the mood (`Encounter.MoodDecides`). They end a conversation after a phrase limit instead of the connection timer: the shipped game's, drawn for their posture and drawn again whenever their mood changes (`Encounter.GetPhraseLimit`, `IsTiredOfTalking`). Every race hails three times at most without a reply (a home fleet gives all its warnings) and says it is waiting twice at most for an answer, 20 seconds apart.
- The Elowan and the Thrynn are rivals (`Encounter.IsFriendOfRival`): a crew member of the other race aboard, or a first comm link of the game with the other race (`PD_General.m_firstContactRace`, saved), makes them greet the crew with their line for it and start in their hostile band, and the Elowan have no dealings at all with a ship that has a Thrynn aboard. A crew member of the aliens' own race makes every word of theirs understood (`PD_CrewAssignment.HasCrewOfRace`).
- The Minstrels, the Nomad probes, the Noah 9 derelict and the Mysterions transmit rather than talk (`Encounter.IsTransmitter`): once the comm link is up their statements are their subject 5 lines in the order of the game data. A line that ends the comm link in the shipped game (every Nomad probe report, every second Minstrel verse: `GD_Comm.m_endsCommLink`) ends it, and the next meeting goes on with the line used least (`Encounter.FindNextTransmission`, by `PD_General.GetCommUseCount`). The Mysterions and the Noah 9 derelict end the link after their last line. The comm screen's race models are looked up through `Encounter.GetAlienRaceModel`, since the scene's list has no slot for the races after the Minstrels.
- A race's own question (`Encounter.FindSpecialQuestion`: the Elowan's "Is thine need for energy dire?", the Veloxi's demand for the Crystal Orb, the Ellipsoid or a tribute, the Thrynn's offer for an artifact or plutonium or of the Black Box) is the first question its aliens ask in an encounter, once (`PD_Encounter.m_specialQuestionAsked`); the race's update handles the answer before `DefaultEncounterUpdate` forgets the question.
- A destroyed alien ship leaves the debris of its vessel's record (`GD_Vessel.m_enduriumVolume`, `m_elementVolumeA` to `C`); the ship takes it aboard once by flying within `Encounter.c_salvageRange` of the wreck (`PD_AlienShip.m_salvaged`, saved).
- Lifeforms (roadmap Phase 6, rebuilt from the 1984 notes by the owner's ruling D3): `GD_Species.ForPlanet` makes a planet's species from its id and bio density with `System.Random` (none without life), and `TerrainLifeforms` places them after every other populator with the planet's seed + 5, so nothing else moves. Its object is made at runtime next to the ruins' (`TerrainGrid.m_terrainLifeforms`); the scene has none. Each one has a `TerrainLifeform` with its hits, stuns and status; the terrain vehicle's Weapon button opens Fire, Switch and Back (`ButtonSet.TerrainVehicleWeapon`), and Fire hits the nearest living lifeform within the mounted weapon's range (`TVFireButton`). `TerrainLifeform.Behave` runs the notes' response to the player every half second within the encounter area (the laser's effect on aggression, approach, attack, flee, wander) and `AttackPlayer` lowers the crew's vitality by the notes' formula; a lifeform is given its populator in `Initialize`, since the lifeforms are placed while the surface is hidden. With nothing to do about the player, a lifeform acts on its mate (`RespondToMate`: the nearest unpaired lifeform in the encounter area, linked both ways): approach, flee, bite and eat. An eaten lifeform goes through `TerrainLifeforms.RemoveEaten`, which takes it out of `m_lifeformList` and off the surface at once, since Scan and Fire walk the populator's children. A lifeform is the prefab of its body plan from `Resources/Lifeforms` (made by `DevTools/LifeformModels/wire.ps1`, which builds the SF - Standard materials; rerun it after a model is rebuilt), standing on its base (`TerrainLifeform.m_groundOffset` 0; a plain shape stands in without one), its "Skin" material tinted per lifeform with a property block on `SF_AlbedoColor`, never through `renderer.material`. Cargo beside a lifeform offers it (`ButtonSet.TerrainVehicleLifeform`), and a recording runs in `TerrainLifeforms.Update`; its value comes from `PD_General.LearnLifeform` (classes, orders and species already known, saved) and is paid on docking (`PlayerData.PayLifeformData`). A capture runs the same way (`StartCapture`) and puts a `PD_Specimen` into the terrain vehicle's `PD_SpecimenStorage`, which counts in the hold's volume, moves to the ship with the rest of the cargo (`Planetside.TransferTerrainVehicleCargo`) and is sold at the Trade Depot (item type 2); reach a hold's specimens through `GetSpecimenStorage()`, since older saves have none.
- Crew injuries go through `PD_CrewAssignment.InjureCrewMember`, never by lowering `m_vitality` directly: at 0 vitality it marks the crew member dead (`PD_PersonnelFile.m_isDead`, saved), passes a dead captain's command down the chain of command, and with nobody left alive ends the game through `CombatController.EndGame`, which destroys the hull so the lost game is never saved. Healing must never raise a dead crew member's vitality.
- Landing and launching are the original's (LAND-OV): each burns the planet's gravity over 40 in tenths of a cubic meter of Endurium (`PD_PlayerShip.GetLandingGravity`, `BurnLandingFuel`: above 8 G the gravity grows by the square root), a launch from the surface without it is refused, a landing without it crashes and one on a planet of more than 7.99 G crushes the hull (`DescendButton` decides, `PlayerCamera.PlayerHasLanded` ends the game through `CombatController.EndGame`); once the science officer's analysis has shown the gravity, Land warns once and a second Land goes down anyway (`SpaceflightController.m_gravityAnalysedPlanetId`, `m_landingWarnedPlanetId`, not saved).
- Lava (the liquid of a molten planet) gives a terrain vehicle in it a warning, and destroys it after 3 seconds there (`TerrainVehicle.IsInLava`, `LoseToLava`): its cargo is lost, the crew is back in the ship, and `PD_TerrainVehicle.m_isLost` (saved) keeps Disembark refusing until `DockingBay.Show` installs a new one for 10,000 MU with Interstel's evaluation.
- The Mechans have the shipped mood, moved only by the answers to their questions (each right one takes 10). Once it makes them friendly they are friendly for good (`PD_General.m_mechan9Unlocked`, saved; `Encounter.UnlockMechans`) and the Mechan fleet at Heaven (encounter 77) lets the ship into orbit and never stops it again; not in an encounter in which the player has fired on the Mechans.
- Of the lines that fit (race, subject, posture), `Encounter.FindComm` says the one used least in the game, the first in the order of the game data on a tie, as the shipped game does (FIND-PHRASE): never at random. The use counts are saved (`PD_General.m_commUseList`, `GetCommUseCount`, `AddCommUse`), so a race's lines take turns across meetings. The answers to questions keep their own order (`GetLastCommId`).
- What the aliens say goes through `Encounter.AddComm`, which fills in the name of the player's captain (`*`) and of the player's ship (`&`) before the words are garbled. Names are stored as they were typed, so the text can hold empty words (two spaces in a row), and the word loop skips them.

## Conventions

Match the style of the file you are editing:
- **Legacy code (most files)**: tabs, Allman braces, spaces inside parentheses (`Foo( a, b )`), `m_` prefix for fields, `c_` prefix for constants, a comment above nearly every statement, public fields for Inspector wiring.
- **Newer code** (`PlanetManager`, `ProceduralAdapter`): 4 spaces, `_camelCase` private fields, `[SerializeField] private`.

From `.github/copilot-instructions.md` (project rules):
- Prefer `FindFirstObjectByType<T>()` over `FindObjectOfType<T>()`, `TryGetComponent` when existence is uncertain, `CompareTag()` over `tag ==`.
- No `GetComponent`/`Find`/allocations in `Update`/`FixedUpdate`/`LateUpdate`; cache in `Awake`. Rigidbody logic in `FixedUpdate`.
- Use explicit `!= null` for `UnityEngine.Object` (not `?.`/`??`, which bypass Unity's destroyed-object check). Null-check singletons outside guaranteed flows.
- Defensive guards are mandatory (past bugs came from these): array bounds, divide-by-zero, `maxIteration` limits on `while` loops, empty-string checks before indexing.
- When fixing errors: compiler errors > runtime exceptions > warnings.

## Working rules

- Label claims CONFIRMED (seen in code, logs or the console), INFERRED (one link unverified: name it) or HYPOTHESIZED. Say what was not tested. Nothing is fixed until it has compiled; say so when a fix only masks a symptom.
- No em dashes anywhere: code, comments, docs, commit messages, PR titles and bodies.
- One small PR per change, on its own branch from the current `origin/master`. Stage files by name, use conventional-commit messages, add a `CHANGELOG.md` bullet under `## [Unreleased]` for every change and update `README.md` for features (`.github/prompts/commitall.prompt.md` has the steps). Do not implement a design-dependent item before the project owner has made the call. Where the research sources under `Research/` document the original game's behaviour, that behaviour is the call (ruled 2026-10-09, `ROADMAP.md` D1); behaviour found only in the 1984 draft notes is not.
- Squash-merge (`gh pr merge <n> --squash`, without `--delete-branch`) only once the `compile` check of the PR's head commit is SUCCESS, never on a red or pending check. `master` has no branch protection, so do not use GitHub auto-merge.
- Before pushing a branch that edits `CHANGELOG.md`, trial-merge it against every open PR branch (`git merge-tree --write-tree --name-only HEAD origin/<branch>`); on a conflict, move the new bullet so an unchanged line separates the two insertions.
- Unity package updates: one per branch, compile-checked before the commit, never in bulk. The CI report lists `com.unity.sdk.linux-x86_64`, `com.unity.toolchain.linux-x86_64-linux` and `com.unity.sysroot.base` as added: container noise, never commit them.
